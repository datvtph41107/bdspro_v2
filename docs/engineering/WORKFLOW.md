# Quy trình phát triển BDSPro V2 — authoritative on main
2026-11-26. Owner: developer. Adopted branch topology and main.go-first by developer request. Detailed operational rules below are the proposed working convention for this setup; developer may challenge/change them in DECISIONS.md. No implementation approval implied.

## 1. Branch ownership and promotion
- main: canonical engineering control documents, accepted research requirements/decisions, overall TODO and handoff. Read origin/main even while working elsewhere. May later receive a verified major milestone by explicit dev -> main PR; until then docs-only, not a release branch. No daily runtime pushes to main.
- dev: integration of completed, reviewed requirement increments; not production. Starts at initial main documentation baseline. No direct runtime work on dev. 
- feat/<requirement>-<scope>, fix/<requirement>-<scope>, refactor/<requirement>-<scope>: one active requirement branch, fork from current dev; daily code/tests/working notes here. A requirement can span multiple chat sessions and commits; do not create branches for each chat arbitrarily. Small commits must be meaningful and preferably buildable; keep incomplete/unverified work on topic branch. 
- Main canonical files are edited only on main; topic branch copies may lag, never treat them as current. Topic owns docs/work/<requirement>/ (session evidence and local checklist). No competing copies of global TODO. Approved policy change recorded on main before dependent implementation. At safe boundary sync main into dev by normal merge/PR (docs-only changes while main is docs-only; inspect diff for any runtime later), then into/create topic as needed. Do not blindly merge stale docs or overwrite changes. If main/dev diverge, inspect and reconcile before proceeding; never force push.
- After all acceptance for a bounded requirement: developer opens topic -> dev PR; verify final head, review, merge only by explicit owner approval. Prefer merge commit or fast-forward preserving individual commits; avoid squash/rebase that erases traceability unless owner chooses. Update main TODO/HANDOFF with actual PR, merge SHA, evidence, next branch/task. For larger approved milestone: dev -> main promotion PR only with explicit owner approval and review of runtime + canonical docs; reconcile main's newer docs, preserve both histories. No automatic release, deployment or branch deletion.
- Repo is public; use synthetic fixtures, no secrets/private data. Branch discipline is a human/agent convention, not claimed server enforcement.

## 2. Start/resume any session
1. Read README, AGENTS, this workflow, REQUIREMENTS, DECISIONS, TODO, HANDOFF from latest origin/main (not old chat or copied branch docs).
2. Fetch refs; resolve active branch in TODO/HANDOFF, inspect actual dev/topic HEAD, ancestry, diff, last session note and user-reported local git status. If no access ask for exact SHA/status; do not invent. Local unstaged work is unknown until user shares it. If branch/plan mismatch, report and reconcile before code.
3. State session ID, requirement ID, task, branch/base SHA, previous verified result, current state, one objective and acceptance. Mark proposed vs accepted; ask only decision-specific questions with evidence/hint/tradeoff. Never reopen accepted constraints without new evidence.
4. Update per-session checklist in topic docs/work; canonical TODO/HANDOFF on main point to active task/session and actual last reported checkpoint, not speculative progress. Agent may propose docs diffs; remote mutations require scope authorization. Developer codes locally; one WIP.
5. Study only needed APIs/implementation via docs/IDE, predict behavior, write/test/debug; record actual commands, versions and output (or NOT RUN), source/diff, failure and decision. No fake CI, benchmark, production or personal mastery.

## 3. Close session (even if incomplete)
Record in topic session note: requirement/task/session ID, branch and base SHA, goal, completed checklist, actual source/commit SHA if any, test outputs/limits, pending questions and next action. A note cannot contain its own final commit SHA; link prior implementation SHA and main later records note commit. Commit code+tests together where coherent, or docs checkpoint separately if useful. Push topic only; do not mark DONE without evidence. Update main TODO/HANDOFF after push with branch, note path/observed SHA, actual state, next action; not a duplicate detailed log. A new chat resumes from these pointers, not a new architecture survey. Unpushed local work remains explicitly local/unverified remotely.

## 4. Commit / PR contract
Commit subject e.g. feat(http): serve local health endpoint [DEV-001]; body states requirement, problem/decision and verification (actual/NOT RUN). No artificial commits to meet quota. PR includes requirement + acceptance, rationale and rejected alternative for material decision, diff scope, test results with environment, risks, rollback/revert, unresolved items; reviewed final HEAD. No merge if failure or incomplete acceptance for the promised scope. Docs-only decisions use own commit and no runtime test claim.

## 5. Code organization: main.go-first
Start production Go source in root main.go, package main, explicit construction, handlers, runtime and helpers as needed; main_test.go separate because Go tooling discovers tests there. go.mod/go.sum, migration SQL, sqlc config/query/generated files remain separate by tool contracts. main.go-first is an initial development constraint, not a claim one file fits all future requirements. No package scaffolding, framework or extraction merely for style/file length. Extract a function/file/package only when a concrete requirement, independent responsibility, testability, dependency direction or change friction earns it; record evidence and decision first. Start with Go standard HTTP proposal DEC-HTTP-01; user can challenge. No auth/DB/Redis before DEV-001. Do not add core framework to justify future use.

## Evidence and release
OWNER DECISION (research/business distinction), SOURCE FACT (SHA/path/lines), OFFICIAL CONTRACT, HISTORICAL INTENT, CONTROLLED TEST (actual environment/output), MEASUREMENT, INFERENCE/NOT RUN. Requirements need success/deny/failure and relevant security/ops costs, not speculative architecture. Personal notes optional (Obsidian/Notion); Git is shared truth. Before public exposure security, recovery, configuration, migration and operations must be approved and verified.
